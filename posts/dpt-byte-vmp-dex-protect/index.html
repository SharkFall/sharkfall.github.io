这里说博客是因为之前已经分析了一部分, 记录在我的博客, 被打断施法后, 复用继续分析

首个 .so 是 lib7d1da9313dc6c48cf078a66b509a4361.so, 在 ProxyComponentFactory.instantiateClassLoader() 里经 JniBridge.m0a() 调 System.load() 完成首次加载。

加载路径长这样:

<dataDir>/dpt-libs/<abi>/lib7d1da9313dc6c48cf078a66b509a4361.so

启动 App 以后, 发现解密的 SO 文件没有删除, 还安静的躺在 <dataDir>/dpt-libs/<abi>/ 里, 倒是省事了, 直接 copy 一份开始分析

instantiateClassLoader 是 AppComponentFactory 生命周期里最早被框架回调的方法, 早于 instantiateApplication, 更早于 Application.attachBaseContext。所以这里是真正意义上的「第一次」加载点, 后续 ProxyApplication.attachBaseContext 里那一套同样是被 f12j 守护的兜底入口, 正常情况下不会重复执行。

壳的整体结构
#

样本 dex 里的关键类(都在 IBDaLQvVQXPIEv 包下):

类 作用
ProxyComponentFactory 继承 AppComponentFactory, 壳入口, 拦截所有组件实例化
ProxyApplication 继承 Application, 兜底加载入口 + 转发到真实 Application
JniBridge native 桥, 所有 native 方法都在这, 还有 System.load
AbstractC0003d 字符串常量仓库 + 派生密钥计算
AbstractC0002c 从 APK 释放并解密 .so 到磁盘
AbstractC0001b .so 解密实现
AbstractC0005f 文件名加密(m18b)
AbstractC0000a 反射 dalvik.system.VMRuntime 取 ABI

整个壳的套路就是经典的 AppComponentFactory 钩子模式:

  1. 在 instantiateClassLoader 这个最早回调里把真实 .so 释放、解密、System.load 进来
  2. native 侧接管后, 通过 rcf() / rapn() 返回真实的 AppComponentFactory 和 Application 类名
  3. 后续所有 instantiateActivity/Service/Provider/... 全部反射转发给真实的 AppComponentFactory

壳字符串解密
#

壳里所有字符串都是这种形式:

public static String m7a(byte[] bArr, byte[] bArr2) {
    int length = bArr2.length;
    int length2 = bArr.length;
    int i = 0;
    int i2 = 0;
    while (i < (AbstractC0000a.class.toString().length() + length2)
                - AbstractC0000a.class.toString().length()) {
        if (i2 >= length) {
            i2 = 0;
        }
        bArr[i] = (byte) (bArr[i] ^ bArr2[i2]);
        i++;
        i2++;
    }
    return new String(bArr, StandardCharsets.UTF_8);
}

看着唬人, 其实 + length2) - class.toString().length() 是自己加自己减, 等价于 i < length2, 纯噪音混淆。剥掉噪音后就是最朴素的循环异或:

// 去混淆后的等价逻辑
for (int i = 0; i < bArr.length; i++) {
    bArr[i] ^= bArr2[i % bArr2.length];
}
return new String(bArr, UTF_8);

按这个思路把 AbstractC0003d 静态块里的几个字节数组还原出来:

字段 还原值
f7e (f3a) com.clljda.alert (包名)
f8f (f4b) 1.1.2 (版本)
f10h (f5c) 674b3b282ad3fd769684d79d77547cb1 (32 位 hex, 壳/APK 标识)
f11i (f6d) lib7d1da9313dc6c48cf078a66b509a4361.so (目标 .so)

派生密钥 —— m15b()
#

AbstractC0003d.m15b() 把上面那些常量拼成解密密钥:

public static void m15b() {
    f7e = new String(f3a).trim();              // "com.clljda.alert"
    f8f = new String(f4b).trim();              // "1.1.2"
    StringBuilder sb = new StringBuilder();
    sb.append(f7e);
    sb.append(m14a(new byte[]{108}, ...));     // 还原出来是 "-"
    sb.append(f8f);
    // 对 "com.clljda.alert-1.1.2" 做类 murmur 哈希
    int i = 0;
    for (byte b : sb.toString().getBytes()) {
        int i2 = (i ^ b) * 1540483477;
        i = i2 ^ (i2 >>> 15);
    }
    f9g = Integer.toHexString(i);              // ← 这就是解密密钥
    f10h = new String(f5c).trim();
    f11i = new String(f6d).trim();
}

所以 f9g 是对 "com.clljda.alert-1.1.2" 做的 murmur 风格哈希, 这个值会同时用于:

  • APK 内加密 .so 的路径段加密(m18b)
  • 落地后的 .so 文件内容解密(m11b)

壳 SO 加载
#

JniBridge.m0a() 是 System.load 的调用者:

public static void m0a(String dataDir) {
    try {
        String abi = AbstractC0000a.m8b();
        File dir = new File(dataDir + "/dpt-libs/" + abi);
        File[] files = dir.listFiles();
        if (files != null) {
            for (File f : files) {
                String path = f.getAbsolutePath();
                if (path.endsWith(File.separator + AbstractC0003d.f11i)) {
                    System.load(path);                       // ← 首个 .so 加载
                }
            }
        }
    } catch (Throwable unused) {}
}

加载的就是上一节解密落地的 <dataDir>/dpt-libs/<abi>/lib7d1da9313dc6c48cf078a66b509a4361.so。
